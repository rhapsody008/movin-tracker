# T5.3a: restore path, start guard, config

## Goal
A database restored from a Velero snapshot must start without resending an old reply or replaying a tool. Before `harness.resume()`, the adapter detects the restore and then does three things:
- it aborts every live task and unsettled submission by id;
- it clears the intake ledger's `queue`, `open` and `cursor`, keeping `recent`;
- it rotates the epoch and re-creates the scheduled tasks.

A normal start behaves exactly as today.

## Design (decided)
**`app/src/durable/startguard.ts`** has no pi-durable import:
- `createStartGuard({store, instance, restoreId, log, signal})` returns a `StartGuard`:
  ```ts
  { check(db: {starts: number; restoreId: string}): Promise<{restore: false | "id" | "counter"; starts: number; restoreId: string}>;
    committed(starts: number): Promise<void> }
  ```
- `check` reads the S3 object `harness/<instance>/epoch.json`. A missing object counts as 0.
  - A failed read is retried with backoff (1 s, doubling, up to 30 s), with a warning each time (`harness start counter unreadable`, `err`, `in`), until it answers or the signal aborts. On abort it throws. `resume()` never happens before the answer.
  - The decision, in this order:
    1. `db.starts === 0` → a new database, never a restore.
    2. A non-empty env id that differs from `db.restoreId` → `"id"`.
    3. `db.starts < s3.starts` → `"counter"`.
    4. Otherwise `false`.
  - The returned `starts` is `max(db.starts, s3.starts) + 1`.
- `committed(starts)` does the conditional put of `{"schema":1,"starts":N,"at":"<RFC 3339 to the second>"}` (`goMarshal`/`Ordered`, field order as written). On `PreconditionError` it re-reads and writes the max. Any other failure only warns (`harness start counter not saved`), because SQLite ahead of S3 heals at the next start.

**The adapter:**
- New option `OpenAgentOptions.startGuard?: StartGuard`. Without it, nothing changes (tests, eval).
- New session doc `movin.start`, `{starts, restoreId}`, initially `{starts: 0, restoreId: ""}`.
- **Between `openedHarness()` and `resume()`:**
  1. Read `movin.start`.
  2. Call `guard.check`.
  3. If it reports a restore, run the restore path (§5.2). Each id from `harness.inspect()`:
     - `abortSubmission` for every unsettled submission;
     - `abortTask` for every live task, whatever its state and whether or not it is background. `"terminal"` is fine.
     
     Any other failure throws: the open fails and the pod restarts. Never call `conversation.abort()` or `waitForIdle()` here, because both start scheduling (G7).
  4. **One acknowledging commit:**
     - `movin.start = {starts, restoreId: <env id, or the old one when env is empty>}`;
     - on a restore, the intake gets `queue = []`, `open = []`, `cursor = 0` (keeping `recent` and `acceptedAt`), and `movin.epoch` gets a new UUID;
     - the `movin.schedule` guard is cleared on a restore.
     
     Then `ensureSchedules()`. On a restore, update the `epoch` closure variable before the `agent` object is built.
  5. Call `guard.committed(starts)`. Its failure only warns.
  6. Call `resume()`.
  
  SQLite is acknowledged before S3 on purpose: the other order would turn a crash between the two into a false restore.
- **Logging:** one info line per start, `harness start`, with fields `starts` and `restore` (`none`/`id`/`counter`). On a restore it also carries `tasksAborted`, `submissionsAborted` and `intakeDropped`.

**Config (`config.ts`):**
- `instance`, from `MOVIN_INSTANCE`. It is required and must be exactly `dev` or `prod`; the error is `MOVIN_INSTANCE must be "dev" or "prod"`.
  - Is `loadConfig` also used by tests or tools that have no instance? Then either make it required only where `serve()` builds the guard, or give the test env `dev`. Choose whichever keeps prod safe (prod must fail without it), and record the choice.
- `restoreId`, from `HARNESS_RESTORE_ID`: optional, trimmed with `goTrimSpace`, at most 128 printable ASCII characters. The error text is yours; follow the existing config errors' style.

**`main.ts`:** build the guard from the S3 store and config, and pass it to `openDurableAgent`. Shutdown's signal aborts a `check` that is still waiting.

**`docker-compose.yml`:** add `MOVIN_INSTANCE: dev` to the `app-ts` and `app-test` services. That is the only root file allowed; the Go services are untouched.

## Step 0 (paste output, then delete the scratch test)
5. Before `resume()`, `abortTask` and `abortSubmission` resolve, start no scheduling, and run no task code. Check this for a delivery and for a sleeping background (schedule) task. T0.2 R2 measured it for a run.
6. After `resume()`, an aborted generation settles its submission, and `afterFailedRun` starts nothing new.

## Mutations (each must fail a named test)
1. `resume()` before the restore path.
2. The intake clear removed.
3. Deliveries skipped.
4. `recent` cleared.
5. The epoch not rotated.
6. S3 written before SQLite.
7. `starts === 0` treated as behind.
8. The id never recorded (so the path runs on every start).
