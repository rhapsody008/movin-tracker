# T3.4 — The prompt

## Goal
`app/src/agent/prompt.ts` builds what the model reads, using Go's texts in v3's layout (plan.md, Design → Prompt):
- **System (instructions):** the rules, plus the documents section when there is one, plus the group line for a group chat.
- **The user message of a fresh context** (the first message, after an idle reset or after a compaction): the entries snapshot, then the date line, then the typed text.
- **Later user messages:** the delta lines (none when nothing changed), then the date line, then the typed text.

It is wired into the adapter's `instructions` and `userContent` hooks. No pi-durable import.

## Design (decided)
- **Rules.** Go's `prompt.go:89-110` text, with the two `%s` filled. The one wording change from v3, `when the list above is not enough` → `when the snapshot is not enough`, is recorded. Pin it with a golden produced by Go (`tmp/t34-golden`; copy `prompt.go` into a scratch `package main` if you need its unexported functions; never edit Go). The TS text must equal Go's text with that one replacement applied.
- **Documents section.** Go's text (`doctools.go:130-166`), with and without vision, the scanned marker and summaries. It is absent, not empty, when no document is readable or the index read fails, and the failure is logged `documents index unavailable for the prompt`. Golden from Go.
- **Group line.** `instructions(key)` gets the conversation's context. Add `{ group: boolean }` to the adapter hook signature (T4 sets it for Telegram groups; web is never a group). The group line is appended to the system text exactly as Go does. Test both cases (`TestGroupSilence` texts).
- **The snapshot** (`prompt.go:64-87` selection, unchanged):
  - drop archived entries;
  - stable sort by `updated` descending;
  - keep 150;
  - stable sort by `created` ascending;
  - use the prompt's `compactEntry` (with `milestone`/`completed` last and notes always empty);
  - marshal with `goMarshal`.

  The header is `Entries snapshot (<n> most recently updated of <m>; use search_entries for the rest): <json>` when there are more than 150 live entries, and `Entries snapshot: <json>` otherwise; both forms are recorded. `m` is the live count, as in Go.
- **The date line.** `Today is 2026-11-11 (Wednesday). Key collection: 2026-10-29. Move-in: not set.` Use the configured timezone, `orNotSet`, and Go's formats. It goes with every user message.
- **Deltas.** The prompt keeps durable state of what the model has seen: `seen: Record<id, string>`, where the value is the entry's compact JSON line as last shown.
  - On a fresh context, `seen` is the snapshot's lines.
  - On a later turn, compute the current lines for all live entries (not only 150) and diff them against `seen`:
    - `added <line>` for a new live entry;
    - `updated <line>` for a changed line;
    - `removed <id> "<title>"` for an entry that was archived or deleted.
  - The block is `Changed since your last message:\n- <line>\n- …`, in `created` order, with no block when the diff is empty.
  - After the run, `seen` takes the current lines of the entries this run's changes touched, so the model's own writes are not echoed back as deltas next turn, while edits from elsewhere still are.
  - Changes to the key or move-in dates show only in the date line.
- **Where `seen` lives.** Extend the adapter, the only pi-durable file:
  - `userContent(key, text, { fresh, group, state }) → { content, state }` and `afterRun(key, result, state) → state`, where `state` is opaque JSON;
  - the adapter persists it in a conversation-scoped doc **in the same commit as the submit**, and the `afterRun` result once the run settles;
  - replay or crash must not double-apply it; say how.
  - Change T3.2's hook signatures accordingly, and update their tests.
- **The first user message order** is snapshot, then date line, then typed text, each separated by `\n\n`, as in the spike. Later messages use the same order with the delta block in place of the snapshot. History still shows only the typed text (T3.2 Q1).
- **Cache prefix.** The system text must be byte-identical across turns while nothing synced. Prove it on the stub: three turns with an edit in between give the same `messages[0]` and an unchanged earlier `messages` prefix.

## Tests (port the Go prompt tests that §7 assigns to T3.4, with Go names; add these)
- **No write between turns:** no delta block, and the earlier messages are an identical prefix (stub).
- **One edit from elsewhere** (the entries service, not the agent) gives exactly one `updated` line.
- **The agent's own `add_entry`** gives no delta next turn.
- **Archive** gives a `removed` line.
- **Reset, idle or compaction:** a fresh snapshot, and `seen` rebuilt.
- More than 150 live entries gives the long header and 150 lines, with notes omitted (`TestPromptLinesForMilestones` and the milestone-last order).
- The date line across midnight in the configured timezone; `not set`.
- The documents section with and without vision, and absent on an index failure (with the log line).
- The group line.
- Rules equal to Go's text with the one replacement.
- A crash after submit doesn't lose or double-apply the `seen` state.

**Mutations (at least 8, on copies):**
- the delta computed against the snapshot rather than `seen`;
- own writes echoed;
- archived entries kept in the snapshot;
- the sort by `updated` ascending;
- notes included;
- `milestone` not last;
- no `removed` line;
- the date in UTC;
- the documents section always present.
