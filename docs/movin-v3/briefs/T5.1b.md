# T5.1b: adapter schedule task and check-in notes

## Goal
Give the durable adapter two generic mechanisms that T5.1c (the check-in) and T5.2 (the nightly docs sync) plug into:
- **one looping scheduled task per name;**
- **a pending note,** which lets a check-in sent at 09:30 reach the model with the chat's next message.

The adapter knows nothing about check-ins or documents.

## Design (decided; T5-plan §2.1 and §2.3)
**The API:**
```ts
// OpenAgentOptions
schedules?: readonly ScheduleSpec[];
export interface ScheduleSpec {
  name: string;
  run(ctx: { target: number | null; signal?: AbortSignal }): Promise<number>; // the next target, epoch ms
}
// Agent
schedule: { rearm(name: string): Promise<void> };
deliver(key, address, parts, options?: { note?: { tag: string; text: string } }): Promise<void>;
// test helper (exported for tests, like abortDeliveries)
inspectSchedules(agent): Promise<{ name: string; state: string; until?: number; target: number | null }[]>;
```

**The task:**
- **Identity:** `movin.schedule` v1. Input `{name}`, checkpoint `{phase: "run", target: number | null}`, registered in `movin.agent`'s `tasks:`.
- **The run phase:**
  1. call `spec.run({target})`;
  2. then `sleepUntil(min(next, now + SCHEDULE_MAX_SLEEP_MS), {phase: "run", target: next})`, where `SCHEDULE_MAX_SLEEP_MS` is 15 minutes.
  
  A wake before the target calls `run` again with the same target. The spec decides what to do then. (T5.1c's tick re-checks its window; T5.2's runs only when `now >= target`.)
- **Errors:** if `run` throws, log `schedule run failed` with `name` and `err`, then sleep 60 s with the same target. A phase must never throw, because a throwing phase faults the task.
- **No spec registered:** if this process has no spec for the task's name, sleep the cap and warn once per name.
- **Ownership:** a dedicated conversation, key `sys:schedule`, made through `conversationFor`. Tasks are `background: true`, so they never hold any conversation's idle (t5-spec §13.2).
- **The guard doc:** `movin.schedule` (a session doc), shaped `{by: {<name>: taskId}}`.
  - `ensureSchedules()` runs on every open, after `openedHarness()` and before `resume()`.
  - For each spec, it creates the task if the doc has none, or if the recorded task is terminal or missing. Log a replacement as `schedule task replaced` (`name`, `was`).
  - The doc update and the task creation happen in one commit.
- **`rearm(name)`:**
  - If the task is sleeping: if Step 0 finds a pi-durable call that wakes a sleeping task early, use it. Otherwise abort the task and create a new one in one commit, updating the doc; the new task runs at once with `target: null`.
  - If the task is running: set an in-memory flag so the current run sleeps 0 afterwards.
  - Never abort a running task.
- **Abort handler:** settles `aborted`, like the delivery's.

**Notes:**
- **Storage:** a conversation doc `movin.notes`, shaped `{pending: [{tag, text}]}`.
- **Writing:** `deliver(..., {note})` writes the note in the same commit that creates the delivery. A note with the same tag replaces the old one.
- **Consuming:** `submit` reads the pending notes and passes them to `userContent` as a new option, `UserContentOptions.notes` (or the equivalent in `prompt.ts`'s API). `commitSubmitted` clears them in the admission commit. A duplicate `requestId`, which takes the attach path, consumes nothing.
- **In the prompt:** `prompt.ts` places the notes after the delta block and before the date line. They go under one fixed header line, `Sent to this chat since your last message:`, with each note's text verbatim (it already starts with Go's `(morning check-in)`), separated by a blank line.
- **Web history:** unchanged. The note never appears in it.
- **Tests:** the prompt test pins the exact bytes, with and without notes.
