# T4.2a: durable intake in the adapter

## Goal
Give the adapter a channel-neutral **intake ledger**, so the Telegram bot (T4.2b) can accept each `getUpdates` batch durably in one commit. Polling must never wait on a turn. Each accepted item becomes exactly one turn or one command, and each turn exactly one delivery, across crashes.

This step also fixes three adapter gaps the ledger exposes.

**Sources:**
- Plan: `docs/movin-v3/briefs/T4-plan.md`, especially §2.2, §2.4, §2.5, the crash-window table in §2.6, and §3 "T4.2a". Approved by ZY on 2026-11-22.
- Decisions: `decisions.md` "T4 plan change" and "T4.3b".
- T4.3b is done: `createDelivery(tx, conversationId, address, parts)`, `Agent.deliver`, and the `movin.outbox.delivery` task, all in `adapter.ts`.

## Design (decided; adjust names only with a reason)

### Ledger doc
A session doc `movin.intake`:
```ts
{ cursor: number;                 // next getUpdates offset (0 = none yet)
  recent: number[];               // accepted item ids, newest last, at most 256: dedupe across redelivery and the restore path
  queue: IntakeItem[];            // accepted, not yet submitted or taken
  open: OpenTurn[] }              // submitted turns not yet settled
IntakeItem = { id: number; key: string; address: OutboxJson; payload: OutboxJson; at: number }
OpenTurn   = IntakeItem & { submission: string; deadlineAt: number }
```
`id` is the Telegram `update_id`. `key` is the conversation key (`tg:<chat_id>`). `address` and `payload` are opaque to the adapter.

### `Agent.intake`
**`accept({cursor, items})`:** one `harness.commit`.
- Skip items whose `id` is in `recent`, or already in `queue` or `open`.
- Append the rest to `queue` and to `recent` (trimmed to 256).
- Cap each key at **64** queued items. An item over the cap is dropped with `log.warn("intake queue full, dropping update", {key, id})`, Go's `telegram chat queue full, dropping update`. It still goes into `recent`, and the cursor still moves.
- Set `cursor` (never lower it; T4.2b passes last id + 1).
- Return the items actually added.

**`state()`:** `{cursor, queue, open}`. A read, no commit.

**`take(id)`:** one commit. Remove the item from `queue`. Returns `true` only for the first caller. This is used for commands, callbacks, refusals and the fixed non-text lines, all at-most-once.

**`settle(id, key, address, parts: OutboxJson[] | null)`:** one commit.
- If `id` is still in `queue` or `open`, remove it, and when `parts` is non-empty, `createDelivery` in the **same** commit.
- If it is already gone, do nothing: settling twice creates one task.

### `SubmitOptions.intake?: { id: number; deadlineAt: number }`
Inside the existing submit commit (`commitSubmitted`, after `conversation.submit`), move the item from `queue` to `open` with `{submission, deadlineAt}`.
- If the item isn't in `queue` (already open, or settled), the submit still proceeds.
- The `requestId` pre-check below makes the duplicate case a no-op.

### `Agent.attach(key, submissionId, {signal}?)`
Resolves to the `RunResult` of an already-submitted turn.
- It is used after a restart for `open` items, and by the watchdog.
- Factor the result-building tail of `submit` (from the settled submission to the `RunResult`) into `resultOf(conversation, settled)`, which `submit` and `attach` share.
- `attach` does **not** run `settlePrompt` (P5b: after a crash the model hears its own writes once more; recorded already).
- `signal` aborts the turn the way `submit`'s does (`abortRun`).

### `Agent.idle(key)`
Resolves when the conversation for `key` has no live run and no live conversation-owned task. That covers deliveries; use `waitForIdle`, which T4.3b confirmed. An unknown key resolves at once.

### Gap 1: the idle wait in `submit`
Inside `serial(key)`, before the idle-reset check, `await conversation.waitForIdle(...)`.
- After a restart `tails` is empty, so a new message could otherwise submit while a recovered run, or a delivery, is still going. That would break the prompt-state read, `configure` and the idle reset.
- It also orders reply N before run N+1 for every channel.

### Gap 2: the duplicate `requestId` pre-check
Before the idle reset, `configure`, the prompt-state read and `submitted()`, look up `tx.submissionByRequest` (confirm the API in the `.d.ts` and cite it) for `(conversation, requestId)`.
- On a hit, do none of those. Attach to the existing submission and return its result.
- No second run, no `movin.prompt` write, no reset, no `configure`.

### Gap 3: closed and faulted
`submit` and `attach` already return `failed/closed` or `failed/faulted` while shutting down. Document on `RunResult` that a caller must treat these as "not settled": the item stays `open` and the restart recovers it. Add a helper `isUnsettled(result)` exported from the adapter, so T4.2b can't get this wrong.

### Restore (T5.3)
Export the doc name as a constant (`INTAKE_DOC = "movin.intake"`). Nothing else yet.

### Import rules
`adapter.ts` stays the only pi-durable importer, with no runtime import from `src/agent` or `src/telegram`.

## Tests

### `adapter.test.ts`
- `accept`:
  - twice with the same ids gives one item;
  - an id in `recent` but no longer queued (settled) is not re-added;
  - the 65th item for one key is dropped and logged, while the cursor still moves and another key is unaffected;
  - the cursor never goes down.
- `take` returns true exactly once, even with two concurrent calls.
- `settle`:
  - twice gives one delivery task and one send;
  - with `null` parts removes the item and creates no task;
  - for an unknown id does nothing.
- Submit with `intake` moves the item to `open` in the submit commit. Check with `observeDocuments`, or by killing between commits in a crash child.
- A duplicate `requestId` causes:
  - no second LLM request;
  - no `movin.prompt` write;
  - no reset or `configure`.
  
  Watch the committed docs, and make the stub fail a second request. It returns the first run's result.
- Ordering: message 2 for a key is submitted only after run 1 **and its delivery** are idle. The delivery's send blocks on a promise the test releases. Assert run 2's first LLM request starts after the release, and that run 2's request contains run 1's answer.
- `attach` returns the same `RunResult` shape as `submit` for an answered run, and for a failed one.
- `idle(key)` resolves at once for an unknown key, and waits for a running delivery.

### `crash.test.ts` (new `crash-intake-child.ts`, or extend an existing child)
- **W3:** kill after `accept`, before any submit. Reopen; the worker logic in the test calls `submit` with `requestId`. One submission, one run.
- **W4:** kill inside a tool of run 1 while item 2 is queued. Reopen, `attach` to item 1's submission: it answers. Then submit item 2: run 2's request contains run 1's answer, and there is one journal record.
- **W5:** kill after run 1 has settled and before `settle`. Reopen, `attach` returns at once, `settle`. Exactly one delivery send.

### Mutations (at least 6)
- remove the idle wait;
- write the prompt state on a duplicate `requestId`;
- `accept` without the `recent` check;
- `settle` without the "still present" check;
- `take` that returns true twice;
- the cap off by one;
- `cursor` allowed to go down.
