# T3.5 — Web chat

## Goal
The web chat runs on the v3 agent. There is one conversation per signed-in email (`web:<email>`), held on the server:
- a reload shows the server history;
- two tabs stay in step;
- replies stream, and change lines come with Undo.

This step wires the agent (T3.2–T3.4) into `main.ts` and the server. Plan: `plan.md:119`.

## Design (decided)
- **Wiring (`main.ts`).**
  - `openAgent` gets `buildTools({ entries, docs, viewer, vision })` and `promptHooks(...)`.
  - The offered tools follow the settings at each turn: `view_document_page` is offered only with `vision`, and the doc tools only when docs are enabled (not `MOVIN_DOCS=off`).
  - Find the per-turn mechanism in `durable-api.md` (`configure({ tools })`, which "applies from the next request"). The adapter sets it before each submit only when it changes, as it does for thinking.
  - If none works, stop and report.
- **`POST /api/chat`.**
  - It accepts Go's body `{"turns":[…]}` for compatibility. It uses **only the newest turn**, which must be a user turn, with Go's 400 texts; earlier turns are ignored, because the history is server-side. Record this.
  - `/think` is parsed from that turn with Go's `parseThink` (port `TestParseThink`).
  - The actor is `{ by: <oauth2 email>, channel: "web" }`, and the key is `web:<email>`.
  - A missing connection gives Go's 400 `no LLM endpoint or model is configured; set one in Settings → LLM` before any submit.
  - **Responses** keep Go's two forms byte for byte (§4.2): non-streaming JSON 200/400/502, and SSE (`delta`, `reset`, `change`, `done`, `error`) when `streaming` is set and `Accept` includes `text/event-stream`.
  - **Change frames:** `change` frames are sent when the run's change lines become known. Emit them from the adapter's tool events (the change lines are in the tool result's `details`); if they can only come at the end, send them all just before `done` and record that.
- **The reply rules.** Map `RunResult` to Go's `Result` and texts (§4.5 and `finish`):
  - `Done.`;
  - the declined text, with earlier changes kept;
  - the cut-off-before-text error;
  - `I looked in the documents but couldn't find an answer to that. …` when `toolsUsed` includes a doc tool and nothing was said;
  - `No answer came back. Try rephrasing.`;
  - `turn_limit` handled as Go's forced-answer outcome (decide the text from `TestChatForcedAnswerWhenModelKeepsCallingTools` and record it);
  - failure details in Go's 502 or `error` shape with `changes` kept.
  
  Put this in `src/agent/reply.ts`, shared with T4.
- **Abort.** As in Go, closing the request aborts the turn. The Stop button stays. Record that a reload during a turn stops it.
- **History route.** `GET /api/chat/history?before=<cursor>&limit=<n>` (default 50, max 200) returns `{ items: [{ role, text, at, changes }], more, cursor }`, where `cursor` is opaque and `items` are oldest first.
  - An unknown key gives `{items:[],more:false}`.
  - Auth is the same as for the other routes.
  - Add it to the router and record it as a new route, not in Go.
- **Two tabs.** Add a `chat` event on the existing `/api/events` stream, for the same email only:
  - `{"type":"user","text"}` when a turn is accepted;
  - `delta`, `reset` and `change` frames as on the request;
  - `done` or `error` with the `Result`.
  
  Frames for one email must never reach another email's stream. The sending tab ignores the `chat` frames of its own request; give each request an id and echo it.
- **The page (`app/static/index.html`).**
  - On load, fetch the history and render the bubbles with change rows and Undo, using the existing `bubble`/`changeLines`.
  - Send only the new message.
  - Render other tabs' `chat` frames live.
  - Remove the 12-turn client array.
  - Keep every existing text and behaviour in §4.3: `Thinking…`, `Stopped.`, `The answer was cut off. Send it again.`, `Something interrupted that. Send it again.` and the model line.
  - Changes on a **user** row (a failed run, T3.3) render under that bubble.
- **Model line.** `model` in `done`/`error`/JSON is the resolved model id, as in Go. A settings change applies on the next message (`TestModelSwitchTakesEffectNextMessage`).

## Tests
- **Port the Go chat tests** with their names, against the stub (`src/llm/stub.ts`) through the real server, adapter, tools and prompt, on MinIO or memory entries and a temp SQLite: `TestChatToolLoop` (both modes, `Move-in set to Sat, 5 Dec`), `TestChatInputErrorsAre400`, `TestChatForcedAnswerWhenModelKeepsCallingTools`, `TestModelSwitchTakesEffectNextMessage` and `TestParseThink`.
- **Reply rules:** a table test over `reply.ts` covering every row of §4.5.
- **History:** after two turns, `GET /api/chat/history` gives four items with changes; paging; an unknown email is empty; another email can't see it.
- **Two tabs:**
  - two `/api/events` clients on the same email both get the `chat` frames;
  - a client on another email gets none;
  - the sender can tell its own request id.
- **Abort:** closing the request ends the run as failed/aborted, and history keeps the user turn.
- **The tools follow the settings:** vision off means no `view_document_page` on the next request (stub).
- **UI check:** extend `app/tools/ui-check` with history rendered on load, a change row with Undo from history, and a second tab receiving a streamed reply. The stub answers through the TS app in compose; add a `LLM` stub sidecar or point the settings at the stub. It must be fully green.
- **Mutations:** at least 10, on copies. For example:
  - chat frames broadcast to every email;
  - older turns used;
  - `/think` not stripped;
  - `Done.` missing;
  - the docs-not-found rule off;
  - changes dropped on error;
  - history unauthenticated;
  - abort not wired;
  - vision ignored;
  - own frames not ignored by the sender.
