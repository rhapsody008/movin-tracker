# movin-tracker v3: decisions

All decided by ZY on 2026-11-20 unless noted. Newest at the bottom of each section. Don't reopen these without asking.

## Direction
- Full TypeScript rewrite on pi-durable (one process, no Go at the end). Reason: wanted a harness framework; one language.
- pi-durable and pi-ai pinned at exactly 1.5.2, adopted now; upgrade only when something breaks. Reason: don't wait on an experimental API; the adapter file limits the damage.
- Conversations per chat. One web conversation, because only ZY uses the web.
- Write tools are replay-safe (change ID from the task ID). Reason: a crash must never write twice.
- Order: conversations, tools and Telegram first; check-in and docs sync as durable tasks after (main session's call, ZY: "go with what you think is optimal").
- chateval is ported and measured, not a hard gate.
- After the Go code is deleted, `app/` moves to the repo root.
- Code is written by the `coder` agent (zy-pi-uep) from the main session's per-step brief; the main session verifies. Every step is reviewed by `ts-reviewer` (TS version of strict-reviewer, with a stricter mode for coder-written code) and ticked only on APPROVE; plus a review per phase. Reason (ZY): the coder model is weaker, so the review is stricter.

## Storage and deploy
- 1Gi RWO PVC on `nutanix-volume` at `/data`, applied by ZY by hand, outside the Flux artifact. Reason: `prune: true` and reclaim policy Delete would otherwise let a rollback destroy it.
- Backup is Velero (already running on zy-all-in-one as the NKP workspace app); no in-app backup. Making it capture the volume's data is a separate ops change and does not block the cutover.
- movin's Velero Schedule covers the PVC/PV only. Reason: secrets and the rest come from Flux or are hand-applied.
- Velero captures the volume through CSI snapshots: label `nutanix-snapshot-class` with `velero.io/csi-volumesnapshot-class: "true"` (no node-agent, no data mover). Reason: cleaner. Accepted: snapshots stay on the same Nutanix storage as the volume (not off-site).
- The app detects a restore both from an explicit restore ID and from a start counter kept in SQLite and S3, and aborts live runs before resuming. Reason: a restored database must not resend old replies, even if the restore ID is forgotten.
- Memory: ~~192Mi request, 512Mi limit~~ → 128Mi request, 384Mi limit, 256 MB Node heap, from T0.2's measurements (main session, under ZY's "go with your recommendation"); re-measured in T6.1.
- Released as `v2.0.0`; Flux pinned to exact versions from T6.3.

## Behaviour
- Prompt: entries snapshot in the first user message, then deltas. Reason: stable prefix, small context.
- After a crash a rare duplicate reply chunk is accepted; a lost reply is not. Entry writes are never duplicated.
- History resets after 6 h idle; compaction as the fallback.
- Commands such as `/undo` stay at-most-once. Reason: "undo my latest" can't be repeated safely.
- A dev bot token and test group are used for the Telegram phases.

## LLM
- Claude native is removed: provider, SDK, cache marks, effort mapping, refusal fallbacks, settings and UI. One OpenAI-compatible endpoint: the NAI gateway (`movin-backend`), already the saved connection. ZY routes Claude through the gateway. Supersedes v2 "two kinds" and refusal fallbacks.
- No special handling for `api.anthropic.com`; that host is not supported. Reason: ZY uses the gateway.
- A `kind:"claude"` section written by v1 is ignored, never rewritten on read. Reason: dev and prod share `settings.json`, and a Go rollback must find it intact.
- Prompt caching is left to the gateway (accepted cost risk).

## Object store (T1.2)
- `put` with `ifMatch: ""` is a caller bug and throws; `null` means create-only. Go used `""` for create-only, but on MinIO `IfMatch: ""` is an unconditional write, so the TS API makes the empty string impossible to send.
- A successful S3 response without an ETag is an error (Go returned `""`, which could later disable the write guard).
- Admin page credential label: from the SDK's `$source` features. Instance-role credentials show "unknown" (this SDK doesn't attribute IMDS); non-credential features alone show "unknown" instead of Go's raw string. Prod uses env keys, so no visible change there.

## Run T1–T3 unattended (ZY, 2026-11-20: "go with recommendations")
- **Change ID carries the args hash.** Change ID = 16 chars of base32(sha256(`epoch|taskId|index`)) + 10 chars of base32(sha256(canonical args)), 26 chars total. A rerun that finds a record with the same 16-char prefix and the same suffix returns it; same prefix, different suffix = collision: logged, write goes ahead with a fresh ULID. No new field in `entries.json` (replaces "the journal record keeps a hash" in plan.md Tools). Go treats change IDs as opaque strings, so rollback is unaffected.
- **Real bucket for dev runs** in T2.3 / T3.5 / T3.6, like `make dev` for Go: one clearly named test entry, undone and deleted afterwards. Everything before T2.3 runs on MinIO.
- **Billed gateway calls** allowed for T3.1 probes and T3.6 chateval (saved key decrypted in memory only, as T0.3).
- **poppler-utils + font** (apk) in the app test image for T1.5; same packages as the Go image. No new npm packages in T1–T3; if one is needed, stop and ask.
- **Commits:** `git-ops` commits locally at the end of each phase (T1, T2, T3), no push, leaving the pre-existing staged renames alone.
- **Review cadence:** the main session verifies every step (lint/test rerun, diff, targeted mutations on compatibility-critical code); `ts-reviewer` reviews once per phase over the whole phase, plus separate reviews for T3.2 (durable adapter) and T3.3 (tools, replay safety). Stop and ask on: a new npm dependency, deletions outside `app/`, real-bucket use beyond the above, a plan error, or a review finding that changes an earlier decision.

## T2 review round 1
- **Errors from `src/llm` never include a body parser's message.** V8's `JSON.parse` quotes its input, so a body that *is* the API key would print it in a 502's `error` and in the log. Decode failures carry fixed tails (`decode models list: invalid JSON`, `decode completion: invalid JSON` — Go's prefixes from `openai.go:126`/`:171`, with a stable tail of our own), and every error that leaves `src/llm` passes through the key scrub as a backstop. Go's own `encoding/json` tails are not reproduced; nothing asserts them.
- **A network error's verb is Go's `urlErrorOp`**: the method's first byte plus the lower-cased rest, so `Get "…"` or `Post "…"` (verified in `tmp/t2x-golden`). Only what follows the URL still differs from Go (`dial tcp …` vs Node's cause text).
- **A missing or null `data` in a models answer is an empty list**, as Go's nil slice is; a non-array is a decode error.
- **`testResult` follows Go's `omitempty`**: no `models` when the list is empty, no `modelsError`/`error` when the text is empty. The page distinguishes "not probed" from "probed and empty" by the key's presence, as Go does.
- **Every struct body is matched case-insensitively, as Go's `encoding/json` folds struct field names**, and when two keys match one field the last in the document wins — position, not exactness (`{"apiKey":"exact","APIKEY":"folded"}` is `"folded"`). Go's answers are in `tmp/t2x-golden`. The entries routes decode into Go *maps*, so they keep exact keys and `"Title"` stays an unknown field; the rule is implemented only in the struct helpers.
- **`closeStreams` is permanent**, like Go's closed `s.closing` channel: a stream that starts after a shutdown sends its first snapshot and then ends. A docs signal that arrives before the SSE handshake is remembered and sent after the first `entries` event, so no frame can ever be written before the headers.
- **The two LLM routes abort their endpoint call when the browser goes away** (`POST /api/settings/llm/models` and `/test`: `res.on("close")` → `AbortSignal` next to the call's own timeout — 15 s for the models list, the connection's `timeoutSec` for the probe). Reason: a closed drawer must not keep a call carrying the key running. The admin storage probe is deliberately *not* wired to it: it has its own 30 s budget and must finish its cleanup, or a cancelled probe would leave `_probe/<ULID>.json` behind.
- **An oversize body is answered, not drained**: 400 with `Connection: close` and no further reads, as `MaxBytesReader` makes Go hang up (F18).
- **`tokenSet` is always `false` in T2**, which is Go's nil-`*telegram.Bot` form; `TELEGRAM_BOT_TOKEN` is in the config and reaches no body and no log. T4's bot supplies its own `tokenSet`.
- **`MOVIN_DOCS` and `GUIDE_FILE` are config**, parsed once in `loadConfig` (`docsOff`, `guideFile`); `main.ts` reads only the config, and `MOVIN_DOCS` accepts only `on`/`off`.

## T2 review round 2
- **A failed docs view at stream start is dropped, not fatal** (G1). Go's select re-reads the index and drops the event when it cannot be read (`server.go:415-419`); a stream that has already answered must not die of it. The queue-then-send path now reuses the same `sendDocs()` as later signals, with one `.catch`, so there is exactly one place that decides.
- **The struct-field lookup accepts two gaps against Go's `encoding/json`** (G2), both recorded in `fieldOf`:
  - a repeated *exact* key. `JSON.parse` keeps the first key's position with the last value, so `{"SCHEDULE":"8:05","schedule":"7:00","SCHEDULE":"9:00"}` resolves to `"7:00"` here and to `"9:00"` in Go, which assigns every occurrence in document order (confirmed: `tmp/t2x-golden` prints `schedule="9:00"`). Closing it needs a positional scanner over the raw body; not done.
  - folding is JavaScript lower-casing, not Go's `strings.EqualFold`/`unicode.SimpleFold`: `{"\u017fchedule":"x"}` matches `schedule` in Go (the long s folds to s; the probe prints `schedule="long-s"`) and does not match here.
- **A top-level `null` models answer is an empty list** (G3): Go's decode of `null` into the struct is a no-op, leaving the nil slice that `Models` turns into `[]`.
- **`scanJsonValue`'s `from` is required** (G4): a defaulted offset is one more place a caller can silently scan from the wrong byte.
- **Text corrections** (G5): the abort comment names the models route's 15 s and the probe's `timeoutSec` separately; the `connectionsCheckingInterval` comment points at the `headersTimeout` set below it; the F4 probe test title says what it checks; the oversize 400 sets `Connection: close` and then writes through `writeErr`, so the body has one writer.

## T3.1
- **One provider, id `movin`.** `src/llm/provider.ts` builds it from the resolved `LLM` on every call (the key, URL and model all come from settings and can change), with the synthesised model entry `{id, name: cfg.model, api: "openai-completions", input: vision ? ["text","image"] : ["text"], reasoning: true, compat: {thinkingFormat: "qwen-chat-template", supportsDeveloperRole: false}, contextWindow: 128_000, maxTokens: 8_192, cost: 0}`. `supportsDeveloperRole: false` keeps the system prompt `role:"system"` as Go sent it; pi-ai's detection would send `developer` for a reasoning model on a standard-looking URL (checked on the stub). `llmModels()` hands back `{models, modelRef}` with `modelRef = {provider:"movin", modelId}`, pi-durable's `ModelRef` shape — T3.1 does not import pi-durable.
- **An empty key sends no Authorization header, via a fetch wrapper.** pi-ai refuses a request with no key at all (`No API key for provider: movin`, `getClientApiKey` in `api/openai-completions.js`) where Go sent no header (`openai.go:58-60`), and neither `createProvider` nor the model entry takes a `fetch`. Proven on the stub: `Authorization: Bearer <key>` with a key, absent entirely without. *(Amended by T3.2, G3: the wrapper moved into `llmModels()`, so `complete()` and the harness share one mechanism.)*
- **Thinking.** `thinkingFor(cfg, think)` is `off` when `thinkOnDemand && !think`, else `medium`, and `complete()` passes it as `completeSimple`'s `reasoning` (`complete()` wants a provider-specific `reasoningEffort` and ignores `reasoning` — a probe mistake worth remembering). The wire then carries `chat_template_kwargs: {enable_thinking: <bool>, preserve_thinking: true}` — **always**, in that key order. Known difference: Go sent the field only when thinking was on demand and not asked (`openai.go:150-152`), so with `thinkOnDemand` off Go left it to the server and pi-ai sends `enable_thinking: true`. Both states are asserted in `src/llm/complete.test.ts`.
- **Other request differences, accepted and not fought:** `stream: true` always (pi-ai's chat-completions path has no non-streaming mode, so the summariser "not streamed" means no delta reaches the caller), `stream_options: {include_usage: true}`, `store: false`, and `max_completion_tokens: 8192` from the model entry (Go sent no cap; the gateway accepted it in T0.3). No `temperature`, no `max_tokens`, no `tools`/`tool_choice` on a `complete()` call, never `x-api-key` or `anthropic-version`. Body key order: `model, messages, stream, stream_options, store, max_completion_tokens, chat_template_kwargs`.
- **Stop mapping** (`stopOf`, from pi-ai's `stopReason` and `rawStopReason`): `toolUse`/any tool-call block → `tool` (tool calls win, as Go's `stopOf`); `length` → `max_tokens`; `rawStopReason "content_filter"` → `refusal`; anything else → `end`. A content filter arrives as `stopReason:"error"` with `rawStopReason:"content_filter"` and `errorMessage:"Provider finish_reason: content_filter"`; mapping it from `rawStopReason` keeps Go's "a refusal is a 200, not an error" (agent-spec §10.12), and it is tested. An unknown finish reason is an error in pi-ai where Go mapped it to `end` — pi-ai wins, and no endpoint the app talks to sends one.
- **Error texts** (`llmError`, `src/llm/errors.ts`). pi-ai has no status field, so the status is read back out of its message: `<status>: <json body>` for a JSON answer, `<status> <body>` for a text one (`utils/error-body.js`), and the body's own `message` is preferred as Go did. Then Go's `endpoint returned <status>: <msg>` with the 300-byte cut shared with `models.ts` (`cutErrorText`), then the key scrub. Measured on the stub, against Go's texts:
  | case | Go | T3.1 |
  |---|---|---|
  | 401 | `endpoint returned 401: Invalid API key` | same |
  | 429 | `endpoint returned 429: <endpoint message>` | same |
  | 500 | `endpoint returned 500: <body>` | same |
  | 503 | `endpoint returned 503: <body>` | same |
  | text body | `endpoint returned 500: plain failure` | same |
  | no body | `endpoint returned 500: ` | `endpoint returned 500: status code (no body)` (pi-ai's words; a known difference) |
  | dropped connection | `Post "…": <cause>` | `terminated: other side closed (UND_ERR_SOCKET)` — pi-ai's text, no URL (known difference) |
  | empty key | no request at all | `No API key for provider: movin` before the fix above; now no header and no error |
  | decode failure | `decode completion: invalid JSON` | not reached: pi-ai parses the stream, a broken chunk is its own error text |
- **The retry classification survives the mapping.** `isRetryableAssistantError` is a text pattern, so `src/llm/errors.test.ts` pins three tables: 429/500/502/503/`other side closed`/`fetch failed`/`socket hang up` retryable; 401 and `insufficient_quota` not; and for every mapped text the answer equals the answer for pi-ai's raw text. The classifier is imported only in tests, from `@earendil-works/pi-ai/utils/retry` (the root index would pull in every adapter).
- **The timeout is `cfg.timeoutSec * 1000` per request.** `complete()` passes it as pi-ai's `timeoutMs` (proven: a `hang` stub answer fails with a timeout at a 0.2 s setting); pi-ai's own SDK retries are off (`maxRetries` unset = 0), so one failure is one attempt, as in Go. On the harness path it is pi-durable's `ConversationStreamOptions.timeoutMs` (`types.d.ts:492`) instead, which T3.2 sets from the same setting.
- **Usage.** `cacheRead` comes from pi-ai's `usage.cacheRead`. Known difference: pi-ai's `usage.input` is `prompt_tokens - cacheRead - cacheWrite` (uncached input), where Go's `In` was the whole prompt, so the `llm call` line's `in` means uncached prompt tokens. Go's own totals formula, `In + CacheRead + CacheWrite`, still yields the true prompt count with pi-ai's numbers, so T3.6 uses it unchanged. The gateway reported no cached tokens in T0.3, so the two agree in practice today.
- **Tool-call fragments.** pi-ai reassembles arguments by index and hands them over as an object (Go kept the JSON string), and it keeps the **first** non-empty `function.name` fragment where Go concatenated name fragments. Real endpoints send the name whole, so the stub sends it whole; the difference is recorded, not worked around.
- **Tool-result images.** Same shape as Go (tool messages stay text, the images follow in one extra user message), different sentence: pi-ai writes `Attached image(s) from tool result:` where Go wrote `Images returned by the tools above.` Not forced (agent-spec §1.6).
- **The summariser** is `createLLMSummariser({settings})` (`src/docs/llmsummary.ts`), wired into `createSyncer` in `main.ts`: `SUMMARY_PROMPT` as the system message, one user message `File: <folder/>name\n\nStart of the text:\n<text>`, no tools, `think: false`, `tidySummary` on the answer, connection resolved per call, `no LLM connection configured` when there is none. With `thinkOnDemand` on (the saved connection's setting) the request carries `enable_thinking:false`; with it off pi-ai sends `true`, which is the thinking difference above. `MOVIN_DOCS=off` still means no syncer at all.
- **No provider SDK in the build.** `src/llm/nosdk.test.ts` loads `src/main.ts` in a child process under `node:module`'s hooks and asserts that no path under `@anthropic-ai/`, `openai/`, `@google/genai/`, `@aws-sdk/client-bedrock*` or `@mistralai/` was resolved: 115 modules, 17 of them pi-ai's, none a provider SDK. `npm ls` shows those packages installed as pi-ai's own dependencies (it hard-depends on them); they are never loaded, and `openai` only would be, lazily, when a request is actually made.

## T3.2
- **Every decision here implements a gap in `briefs/durable-api.md`; the decisions themselves are in `briefs/T3.2.md` (G1-G10) and are not reopened.**
- **G1, the directory is our own session document.** pi-durable mints conversation IDs and has no lookup by key (`types.d.ts:21`, `:744-749`, `:1116-1180`), so `movin.conversations` (`{by: {<key>: conversationId}}`) is the index. `conversationFor(key)` reads it and, when the key is new, creates the conversation with `createConversation({init})`, whose `init` writes the entry *inside the creating commit* (`harness/types.d.ts:485-490`): a conversation and its directory entry can never disagree. `history()` uses a non-creating lookup, so a read for an unknown key answers `{items: [], more: false}` and makes no conversation.
- **G2, the forced answer is a `beforeProviderRequest` patch.** `N = max(cfg.maxToolRounds, 1)`; a `GenerationTask` hook sets `tool_choice: "none"` once `pi.live.run.turns >= N`, and `configure({maxTurns: N + 1})` stays only as the backstop. `tool_choice` is in no settings object (`harness/types.d.ts:493-509`) and `maxTurns` alone ends a run `turn_limit` instead of answering (`generation.js:897-906`), so the body patch is the mechanism, exactly as durable-api.md §6 recommends. **Known difference from Go:** Go ignores the tool calls a model still emits on the forced round; pi-durable runs them and the run then ends `turn_limit` — tested, and T3.5 maps `turn_limit` to Go's reply rules. The tester for this lives on `src/llm/stub.ts`, not faux: pi-durable's hook rides on pi-ai's `onPayload`, and **the faux provider never calls it** (`pi-ai/dist/providers/faux.js`, `stream()`: it calls `onResponse` only), so a faux test could not see a request body at all.
- **G3, the keyless fetch now lives in `llmModels()`.** `provider.ts` wraps the chat API (`ProviderStreams`) with `fetch: withoutAuthorization` and resolves the placeholder key `"unused"` when the saved key is empty, so a request carries no `Authorization` header. `requestOptions()` is gone: both `complete()` and pi-durable's harness go through that one `Models` collection, and `ConversationStreamOptions` carries neither `apiKey` nor `fetch` to override it with (`durable-api.md` §4). Proven through the harness on the stub (`adapter.test.ts`, "the keyless connection through the harness"). One follow-on edit outside the brief's paths: `tools/llm-check.ts` imported `requestOptions` and now passes nothing (accepted by the main session).
- **G4, the change ID has no index.** `ToolExecutionApi` has `taskId` and `callId` and no call index (`harness/types.d.ts:191-193`), so T3.3 builds `base32(sha256(epoch|taskId))` plus the args-hash suffix. T3.2 only exposes `taskId`, `callId`, `epoch` and `conversationKey` to a tool (`ToolContext`), and creates `movin.epoch` with the database on first open.
- **G5, streaming is commit-granular and the events are neutral.** A `conversation.watch()` per submit turns `pi.live` into `{type:"delta"}` (incremental: each event is the text appended since the last one), `{type:"tool", name, status}`, `{type:"retry", at, error}` and `{type:"reset"}`. Accepted: partials arrive at `settings.progress.partialIntervalMs` (100 ms) rather than per token. `reset` means "drop what you showed" — a preamble before a tool call (Go's rule) *and* a partial a retry discarded; a client that concatenates deltas and clears on `reset` is correct for both. The committed answer entry is also a source, because a fast provider commits no partial at all (faux does exactly that).
- **G6, idle reset and compaction replace Go's trim.** `IDLE_RESET_MS` = 6 h (`IDLE_RESET_MS` in `adapter.ts`; Go's bot used 2 h and never set it). Before a submit, a gap over it calls `conversation.reset(undefined)`; storage and history keep everything. `CONTEXT_BUDGET_TOKENS` = 48 000 is expressed as `reserveTokens = contextWindow - 48 000` against the model's window (`types.d.ts:518-541`: generation compacts above `contextWindow - reserveTokens`), with `keepRecentTokens = 16 000` and `backgroundTokens: 0`; the comment in the file says the budget bounds the cost because the gateway does no prompt caching (T0.3). There is no Go-style 12-turn trim. `fresh` — "this run starts a new context" — is "the context's head marker differs from the one the previous run started with", recorded in `movin.activity`; that covers the first run, a reset and a compaction, and it is what T3.4 re-sends the snapshot on.
- **G7, resume is the only thing open does.** The adapter calls `harness.resume()` right after `open` and never `abort()`/`waitForIdle()`, because those start scheduling themselves (`harness/types.d.ts:824-834`); aborting live work before `resume()` is the restore path, which is T5.3. The file says so at the call.
- **G8, failures are neutral.** `{status:"answered", text, stop, usage}` takes `stop` from the final message by `stopOf` (so a refusal or a cut-off survives) and sums the usage of every assistant entry from the run's input to its answer, as Go's `turn.usage` did. `{status:"failed", reason, detail}` keeps pi-durable's reason verbatim (`model_error`, `turn_limit`, …) and passes the detail through `llmError`, so a failed request's text is scrubbed of the key. A settings read that fails answers `reason: "settings_error"`, an adapter-level reason outside the library's vocabulary; T3.5 shows the generic failure line for it.
- **G10, thinking costs a commit only when it changes.** `configure()` is called once per submit with whatever differs: `model`, `thinkingLevel` (`thinkingFor(cfg, think)`), `maxTurns` (`N + 1`) and `instructions`. With the level unchanged the second turn commits nothing (tested by watching committed document changes). The first request of a new conversation still writes `pi.agent` twice — once by the library's creation and once by that configure — which is a one-off per conversation.
- **One lint rule, two gates.** `biome.json`'s `noRestrictedImports` now covers `@earendil-works/chord` as well as `@earendil-works/pi-durable` (subpaths included), with `src/durable/adapter.ts` the only override; `src/durable/imports.test.ts` re-scans `src/**` for both specifiers so `make test` fails too, and asserts it finds the adapter's own imports so the scan cannot pass vacuously. Tests reach the harness only through the adapter's two test helpers, `observeDocuments()` and `whenIdle()`, and the crash fixture `src/durable/crash-child.ts` imports the adapter and pi-ai but never pi-durable.
- **Test seams in `openAgent`.** `models?: (cfg) => ModelWiring` replaces `llmModels(cfg)`, which is how a test gets pi-ai's faux provider into the harness; `now` is the harness clock (the idle reset and `fresh` use it); `retry` shrinks `baseDelayMs` to 1 ms. Nothing else in the adapter is configurable for tests.
- **`DATA_DIR` and the agent's life.** `Config.dataDir` is `DATA_DIR`, default `/data`, the db at `<dataDir>/harness.db`. `serve()` opens the agent after the listener (so a slow volume never delays readiness), exits 1 on `closed: {kind: "failed"}` so Kubernetes restarts the pod, and closes it on shutdown. No route uses it yet (T3.5), so `startServe` does not own it and the T2 tests are untouched. The `app-ts` compose service gets `DATA_DIR=/tmp/movin-data` because that container has no volume.

## T3.2 review round 1
- **The `retry` event is scrubbed and Go-shaped.** `pi.live.generation.retry.error` is pi-ai's own composed text (`generation.js:639` keeps `message.errorMessage`), so it goes through `llmError(…, apiKey)` before it reaches `onEvent`: `endpoint returned 503: …` with the key redacted, the same text every other error path shows. Tested with a 503 whose body echoes the key.
- **An abort stops the run, not just the queue.** `submission.abort()` only withdraws an input that is still `queued`; an idle input is placed at admission, where it returns `"already_placed"` (`submissions.js:104-115`) and nothing stops. So an abort calls `submission.abort()` and, on `already_placed`, `conversation.abort()`, which marks and signals the run and withdraws queued inputs. An already-aborted signal acts at once, and every promise on that path is caught and logged: a rejection racing a close became an unhandled rejection, which Node 24 turns into a process exit. Tested against the stub's hanging response (the run ends `unanswered`/`aborted`) and against a close at the same moment (no `unhandledRejection`).
- **A close during a run ends the turn as a result, not a throw.** `submission.wait()` rejects with `Harness is closed`, and `submit()` answers `{status:"failed", reason:"closed", detail:"Harness is closed"}` (scrubbed through `llmError`). The activity record is skipped and logged. Reason: a chat route that receives a rejection during a shutdown has nothing useful to say, and a rejected promise in a route is how a pod dies. Tested.
- **One key at a time, for writes.** `submit` and `reset` are chained per key on a `Map<key, Promise>` tail, dropped when it settles, because creation, idle reset, `configure` and the run all span `await`s: two first messages both saw no directory entry and created two conversations (one dropped out of the directory), and a second turn's `configure` could change the agent of the run in flight. The directory's `init` now throws when the key is already set, and the creator looks the key up again — which also covers a second process on the same volume. **`history()` is deliberately not in that chain:** it is a read, so a page reload during a 30 s turn returns at once (a turn in flight shows what is committed of it so far), and it never creates a conversation — an unknown key answers `{items: [], more: false}` and writes nothing. Both are tested against the stub's hanging response.
- **History shows what the user typed.** A turn is submitted with `entry: {kind: "movin.user", data: {text, actor?}}`: the model still sees the submitted `content` (from T3.4, the snapshot or delta), and `history()` reads `data.text` (durable-api.md §2). `actor` (Go's `by`) is passed through now and used by T3.3's change rows.
