# T4.2b: the Telegram bot — polling, auth, workers, delivery wiring, status

## Goal
A running bot. The poll loop accepts updates into the durable intake ledger (T4.2a). Per-chat workers turn each item into a turn, a fixed line, or (in T4.4) a command. Replies go out through the durable outbox (T4.3b), using the T4.3a formatting. The admin page shows Go's status. After this step a message to the bot is answered end to end, and survives crashes.

## Design (decided)

### Ledger shapes (opaque to the adapter)
- **`key`:** `tg:<chat_id>`.
- **`address`:** `{chat: number, messageId: number, group: boolean}`.
- **`payload`:** everything the worker needs after a restart. That means the kind (`message` | `command` | `callback` | `nontext`), the trimmed text, `from` `{id, first/last/username as Go uses them}`, the chat type and title, and the callback id and data. Keep it minimal, but enough for auth check 2 and the rejected-list row.

### Poll loop (spec §2.1)
- `getMe` with Go's backoff, then `running=true` and `botUsername`.
- `setMyCommands(Go's list)`; a failure is only logged.
- Then loop `getUpdates(cursor, 50)`:
  - **409:** wait 15 s (ConflictWait), and set `lastError`.
  - **429:** wait `retry_after`.
  - **Other errors:** Go's `pollRetry` backoff.
  - **Success:** `lastPollAt`, plus `lastUpdateAt` when the batch is non-empty.
- `allowed_updates` is the client's.
- **Starting cursor:** `intake.state().cursor`. **Update-id reset guard:** Telegram picks a random `update_id` after a week with no updates, so a stored cursor could hide new updates forever. If no batch has been accepted for 6 days (in memory, and at startup by the ledger's newest `at`, falling back to 0 when unknown), poll with offset 0 once. Unconfirmed updates are deduped by `recent`. Pin this in a test with a fake clock. If deciding "the ledger's newest `at`" needs an adapter field, add `acceptedAt` to the `movin.intake` doc and `state()`. That is the one adapter change this step may make; record it.

### Per batch, in order
1. Migration notice (spec §3.4).
2. Ignore anything that is not a message or a callback with a message (spec §2.2).
3. Auth check 1 (spec §3.1). A refusal is added to the in-memory rejected list (newest first, max 10) with the log line, and is **not** accepted. Refused callbacks get their toast **after** the commit.
4. Classify:
   - callback → `callback`;
   - empty trimmed text with a document, photo or voice → `nontext`;
   - empty without one → drop silently, not accepted;
   - starts with `/` → `command` (spec §6.1). A `/cmd@otherbot` is dropped here, before any side effect (trap §11 item 13);
   - otherwise → `message`.
5. One `intake.accept({cursor: last update_id + 1, items})`. Nothing is sent before it.
6. Wake the workers for the added items.

### Workers (one async loop per key, draining in ledger order)
For each item:
1. `await agent.idle(key)`.
2. **Auth check 2**, against the settings resolved now. A refusal is `take` + reject row, with no reply.
3. By kind:
   - **`message`:**
     - Start typing (Go's §4.6: at once, then every 4 s, errors ignored).
     - `parseThink`, then `submit(key, group ? name+": "+text : text, {requestId: "tg:<id>", intake: {id, deadlineAt: now+15 min}, actor: {by: name, channel: "telegram"}, group, think, display: <as typed>, signal: watchdog})`.
     - Stop typing.
     - If `isUnsettled(result)`: leave the item and stop this worker. This is shutdown, and startup recovery owns it.
     - Otherwise render with `channelReply(result, model, group)`, then `replyMessages(…, {timedOut})`, then `intake.settle(id, key, address, parts)` (`null` parts when silent).
     - The `model` argument should be whatever the web chat route passes; follow `server/chat.ts`.
   - **`message` that is a bare `/think`, or `nontext`:** `settle` with `textMessages(THINK_HINT or NON_TEXT_REPLY, address)`. No model call.
   - **`command`:** `/think <q>` is the message path. In this step, every other command is `take`, then `deliver(textMessages(unknown-command line or a T4.4 placeholder))`:
     - commands Go knows (`/start /help /recent /undo /sync /checkin`) → **log `command handled in T4.4` and send nothing**;
     - truly unknown → Go's `I don't know /<cmd>. Send /help to see what I can do.` (spec §6, trap §11.13: echo the original case).
   - **`callback`:** `take`, then `answerCallbackQuery` with empty text. T4.4 replaces both placeholders through one `handleCommand`/`handleCallback` seam; design that seam now.

### Startup recovery
Before polling:
- Read `intake.state()`.
- For each `open` turn, start a waiter: `attach(key, submission, {signal: watchdog from the stored deadlineAt})` with typing, then render and `settle`, as above.
- Hand `queue` items to their workers. The workers' `idle` wait orders them after the recovered run.

### Watchdog
An `AbortSignal` that fires at `deadlineAt`. Its reason marks a timeout, so the render passes `timedOut: true`. Clear the timer when the turn settles.

### `format.ts` addition
`textMessages(text, address, keyboard?)` splits with `MAX_MESSAGE`, threads the first part in groups, and puts the keyboard on the last part. Have `replyMessages` use it, so there is one assembly. The golden must stay byte-identical.

### `outbox.ts`
`send(address, part)` → `client.sendMessage(part)`. Map errors onto `OutboxError`:

| Error | Mapping |
|---|---|
| 429 | `retryAfterMs = retry_after * 1000` |
| 400, 403 or any other 4xx | `permanent` |
| 5xx, transport errors, timeouts | plain (transient) |

Every failed send also sets the bot's `lastError` with Go's text (`telegram sendMessage failed` + the error), and the error text never holds the token.

### Status (spec §9)
- `status()` returns an `Ordered` built in Go's field order with Go's omission rules: `rejected` is always an array; `chatId`/`fromId` are strings; times use Go's `time.Time` JSON (reuse the existing helper).
- `checkinStatus()` is `{"until":"20:00"}`.
- `lastError` is never cleared.
- `tokenSet` is true when there is a token.

### `main.ts`
- When `config.telegramToken !== ""`:
  1. create the client;
  2. pass `outbox` to `openAgent`;
  3. after the agent opens, start the bot;
  4. give `ServerDeps.telegram` the status source.
- On shutdown, stop polling (abort `getUpdates`) before `agent.close()`. Turns in flight stay durable (spec §2.3) and are recovered at the next start.
- Without a token: no bot, and today's status answer.
- The allowlist comes from the resolved settings, `env` plus the saved settings, as `admin.ts` already resolves it. Reuse that resolver; don't re-read env.

### New tests
- A duplicate update in two batches is one turn and one reply.
- Crash before the cursor moves: Telegram redelivers, and the update is processed once.
- The watchdog fires at the stored deadline, including after a reopen, and sends the `TIMED_OUT_DETAIL` failure line. Use a fake clock or a short deadline.
- A 429 on `getUpdates` waits `retry_after`.
- The migration row appears in the rejected list.
- Status JSON order and omissions match Go, byte for byte against a Go golden if one is cheap (`app/golden/t42`), otherwise a pinned literal citing `bot.go:74-83`.
- Auth check 2 refuses an item queued before an allowlist change.
- A `/cmd@otherbot` causes no side effect.
- The update-id reset guard.
- `outbox.ts`'s error mapping.

### Crash test
The parent hosts the fake Bot API and the LLM stub. SIGKILL the child mid-turn (inside a tool or a hanging LLM response). The second child, or the parent reopening, produces exactly one reply message and one entry. Use MinIO, like the T3.3 and T4.2a W4 cases.

### Mutations (at least 8)
- accept before auth check 1;
- send before the accept commit;
- no auth check 2;
- the watchdog ignoring the stored deadline after a reopen;
- 409 without the wait;
- private replies threaded;
- `isUnsettled` results settled;
- `/cmd@otherbot` executed.
